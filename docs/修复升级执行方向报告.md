# ChatGPT-Fix 修复/升级当期修复版执行方向报告

生成日期：2026-07-28  
适用仓库：`D:\project\ChatGPT-Fix`  
目标版本线：`release/0.1.0`  
建议方向：延续现有 `ChatGPT-NTFS-Fix` 同类方案，以 `launcher/manager + 版本化隔离 baseline` 作为主实现；不以独立 watchdog 作为主修复路径。

## 1. 结论摘要

当前修复版已经接管 ChatGPT/Codex Desktop 启动入口，但它固定运行旧官方包副本：

- 当前系统注册官方包：`OpenAI.Codex_26.721.4979.0_x64__2p2nqsd0c76g0`
- 当前本地修复 baseline 来源：`OpenAI.Codex_26.707.8479.0`
- 当前快捷方式目标：`C:\Users\32893\AppData\Local\Programs\Codex-NTFS-Fix\baseline\app\ChatGPT.exe`

因此，当期最重要的升级方向不是直接清进程，也不是另起常驻 watchdog，而是把当前修复版升级为“每次启动前能发现最新官方包、生成/复用对应版本隔离 baseline、再从 launcher 启动”的自更新式本地修复器。

推荐主线：

```text
Start Menu shortcut
  -> ChatGPT-NTFS-Fix launcher/manager
      -> read-only discover latest OpenAI.Codex Appx/MSIX package
      -> compare current baseline state.json
      -> if version/hash drift: stage a new isolated baseline
      -> apply local mitigation only to isolated baseline / launcher environment
      -> atomically switch current baseline pointer
      -> launch isolated ChatGPT.exe
      -> report MCP/uv/python/node/pwsh lifecycle candidates for reviewed handling
```

## 3. 不采用独立 watchdog 作为主方案的原因

用户已经明确指出：watchdog 不够稳定。本报告据此调整实现方向。

独立 watchdog 的问题：

- 容易误判活跃任务、用户手动终端或外部 MCP；
- Windows 下 stdout/stderr 继承、父进程消失、命令行截断会让所有权判断不稳定；
- 常驻监控本身会增加一个新的故障源；
- 它更像事后补救，不解决“官方更新后修复版仍跑旧 baseline”的核心漂移。

因此，进程生命周期治理应当依附于 launcher/manager 的所有权模型，而不是另起一个外部清道夫。换句话说，主方案不是“发现残留后杀掉”，而是：

1. 从正确的新官方包生成隔离 baseline；
2. 由 launcher 统一启动；
3. 在隔离启动上下文内最小化 MCP 重复拉起；
4. 通过配置、环境、所有权标记和安全退出协议减少残留；
5. doctor 继续报告残留候选，但不自动清理。

## 5. 执行阶段

### Phase 0：冻结当前证据与只读门

动作：

1. 运行 `scripts/chatgpt-fix-doctor.ps1 -Json` 生成当前快照。
2. 保存为 `records/doctor-runs/<timestamp>.json`。
3. 记录：
   - 官方包版本；
   - baseline 来源版本；
   - ChatGPT 快捷方式；
   - lifecycle candidate summary；
   - `.codex` 体积；
   - manager 签名与 hash。

验收：

- doctor `read_only = true`；
- 不执行 installer；
- 不终止进程；
- 不清理 `.codex`；
- 不改 WindowsApps。

### Phase 1：实现 manager dry-run

目标：先让 manager 能回答“会做什么”，不实际做。

dry-run 输出应包括：

- 发现到的最新官方 `OpenAI.Codex` 包；
- 当前生效 baseline；
- 是否需要新建 baseline；
- 新 baseline 目标路径；
- 将复制的文件数量/总大小估算；
- 将写入的 state/current/log 路径；
- 快捷方式是否需要切换；
- lifecycle 风险摘要；
- 明确 `would_modify_windowsapps=false`。

验收：

- dry-run 可重复运行；
- 输出 JSON schema 固定；
- 能检测当前 `26.707.8479.0 -> 26.721.4979.0` 漂移；
- 不产生除 dry-run 报告以外的写入。

### Phase 2：实现版本化 baseline staging

目标：在用户批准后，把最新官方包复制到隔离 staging，再原子发布为 baseline。

建议流程：

1. `stageRoot = baselines\.staging\<packageFullName>-<timestamp>`；
2. 复制官方包 `app\` 到 staging；
3. 生成 `hashes.json`；
4. 验证关键文件：
   - `ChatGPT.exe`
   - `Codex.exe`
   - `resources\app.asar` 或实际存在的等价资源；
5. 写入 staging `state.json`；
6. 重命名 staging 为最终 baseline；
7. 更新 `current.json` 指针。

验收：

- 源包 `Get-AppxPackage` 注册事实与 `state.json` 一致；
- staging 失败可删除 staging，不影响 legacy baseline；
- 发布前后官方 WindowsApps hash 不变；
- `current.json` 切换可回滚。

### Phase 3：迁移现有修复逻辑

目标：把当前 `ChatGPT-NTFS-Fix` 已验证过的启动/NTFS 规避逻辑迁移到新 baseline。

必须遵守：

- 不改官方包；
- 不污染全局 `.codex`；
- 不默认更换用户 CODEX_HOME；
- 不默认清理日志；
- 不绕过签名/来源记录。

可迁移项：

- 直接从隔离目录启动 `ChatGPT.exe`；
- 固定 profile 目录；
- state.json 记录 `SourcePackageVersion`、hash、安装时间、回滚点；
- 启动前后健康检查；
- 失败回滚 legacy baseline。

### Phase 4：MCP/工具生命周期治理

主策略不是独立 watchdog，而是减少重复启动与明确所有权。

建议顺序：

1. 配置层先做 MCP allowlist/denylist dry-run；
2. 对高重复 MCP（如 Bocha、Hermes、Open Design）输出“建议禁用/按需启用”报告；
3. launcher 启动时注入只读标记环境变量，例如：
   - `CHATGPT_NTFS_FIX_BASELINE_ID`
   - `CHATGPT_NTFS_FIX_LAUNCH_ID`
4. doctor 按 launch id / 父链 / 命令族汇总 lifecycle candidates；
5. 只有在后续明确授权的 maintenance mode 中，才处理隔离 baseline 明确拥有且已空闲的后代进程。

验收：

- doctor 能显式列出 `python.exe`、`uv.exe`、`node.exe`、`pwsh.exe`；
- 不把 Hermes Studio 等用户主动启动进程误归类为可处理对象；
- 不自动 kill；
- 输出 `would_cover_by_lifecycle_policy` 而不是 `would_kill`。

### Phase 5：日志与图片治理

日志治理必须独立于 baseline 升级，不要混成一个安装动作。

建议：

1. doctor 继续报告：
   - `.codex/sessions` 总大小；
   - 最大 JSONL；
   - `logs_2.sqlite` 大小；
   - 图片/base64 痕迹；
2. manager 提供 `maintenance --dry-run`；
3. 后续 maintenance mode 只在 ChatGPT/Codex 退出、文件未被占用、用户确认后执行；
4. 首先实现归档/复制备份，不直接删除；
5. `history.max_bytes` / MCP disabled 配置只生成建议 diff，不直接写全局配置。

验收：

- 不触碰活跃 session；
- 不提交 raw `.codex` JSONL；
- 不暴露 token/cookie/key；
- 所有清理都需要独立批准。

## 8. 推荐下一步

下一步建议不是执行安装，也不是清理残留进程，而是实现 `manager --dry-run --json`：

```powershell
# 示例命令名，具体二进制/脚本名以后续实现为准
ChatGPT-NTFS-Fix-Manager.exe doctor --json
ChatGPT-NTFS-Fix-Manager.exe upgrade --dry-run --json
```

第一版 dry-run 只需证明：

1. 它能发现 `OpenAI.Codex_26.721.4979.0_x64__2p2nqsd0c76g0`；
2. 它能读取当前 legacy baseline `26.707.8479.0`；
3. 它能计划创建新的 versioned baseline；
4. 它不会修改官方包；
5. 它不会杀进程或清 `.codex`；
6. 它能把 `python.exe` / `uv.exe` / MCP 残留作为 lifecycle evidence 汇总，而非作为直接 kill 目标。

等 dry-run 报告通过后，再进入 baseline staging。这样既延续了当前 `ChatGPT-NTFS-Fix` 已验证的 side-by-side 思路，也避免把不稳定的 watchdog 当作核心修复。
